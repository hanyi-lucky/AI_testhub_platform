一、项目一句话介绍

TestHub 是什么？
一个"AI帮你写测试用例 + 自动帮你跑测试 + 出漂亮报告"的测试管理平台。
后端 Django 4.2 + 前端 Vue3 + 数据库 MySQL 8.0 + 消息队列 Redis。

把它想象成一个智能厨房：

  • 厨师长(Django)：负责接收订单、分配任务
  • 菜单(前端Vue3)：用户看到和操作的界面
  • 冰箱(MySQL数据库)：存所有数据
  • 智能炒菜机(AI模型)：自动生成测试用例
  • 外卖小哥(Celery异步任务)：后台默默跑定时测试
  • 门禁卡(JWT Token)：进门要刷卡，卡过期要换新卡

3.1 用户登录全流程

一句话：用户输账号密码 -> 后台校验 -> 发两张门禁卡 -> 短卡(60分钟)日常用，长卡(7天)专门换短卡。

关键代码位置

  • 登录函数：apps/users/views.py -> login_view 函数
  • JWT配置：backend/settings.py -> SIMPLE_JWT 字典
  • 登出拉黑：apps/users/views.py -> logout_view 函数

关键技术细节

  • 细节1为什么不直接用SimpleJWT自带的TokenObtainPairView？因为自己写login_view可以一次请求同时返回user信息+access+refresh，前端少发一次请求。
  • 细节2ROTATE_REFRESH_TOKENS=True：每次刷新都换新的Refresh Token，旧的立即作废。
  • 细节3BLACKLIST_AFTER_ROTATION=True：旧Token写入黑名单数据库表，即使被盗用也用不了。
  • 细节4登出时前端把Refresh Token发过来，后端调token.blacklist()拉黑。

3.2 接口测试全流程(核心中的核心)

一句话：用户选好接口 -> 合并环境变量 -> 把${xxx}表达式全换掉 -> 发HTTP请求 -> 做断言 -> 提取响应字段给下一步用 -> 出报告。
用户点击执行套件 | v views.py -> ScheduledTaskViewSet.run() (触发入口) | v _execute_task_async() -> 开线程 -> execute() | v _execute_test_suite(task) 或 _execute_api_request(task) | v utils.py -> execute_test_suite(test_suite, env, user) | +-- 1. 创建VariableResolver()(变量解析器) | +-- 2. 创建TestExecution记录(RUNNING) | +-- 3. 获取套件中的请求列表(按order排序) | +-- 4. 合并环境变量：base_variables = GLOBAL + LOCAL | +-- 5. 逐个执行请求 --------------------------+ | | +-- 合并变量：{**base_vars, **runtime_vars}| | | +-- resolver.resolve(url) <- ${base_url}换成真实值 +-- resolver.resolve(headers) +-- resolver.resolve(body) | | | +-- requests.request(method,url,...)发HTTP请求 | | +-- 提取响应extract_from_response()->写入runtime_vars | (例如提取token给下一个请求用) | | | +-- execute_assertions()做断言： | | - status_code == 200? | | - response.text包含"success"? | | - json_path $.data.token存在? | | - response_time <= 3000ms? | | | +-- 保存RequestHistory | | | +-- 下一个请求 <-- runtime_vars已更新 ----+ | v 生成Allure报告 / 简单HTML fallback报告

关键代码位置

  • 执行入口：apps/api_testing/views.py -> _execute_task_async(第1688行)
  • 核心执行：apps/api_testing/utils.py -> execute_test_suite(约第110行)
  • 变量解析：apps/core/variable_resolver.py -> VariableResolver.resolve()
  • 请求构建：apps/api_testing/request_utils.py

关键技术细节

  • 细节1变量分为两层：base_variables(环境变量，不变的) + runtime_vars(运行时提取的，每步都可能变)。合并时runtime覆盖base。
  • 细节2接口关联怎么实现：上一个请求的响应里提取token，写入runtime_vars，下一个请求用{{token}}引用。
  • 细节3断言类型有6种：status_code/response_time/contains/json_path/header/equals
  • 细节4如果没有Allure，自动fallback到简单HTML报告

⭐ 进阶：两套变量替换机制详解

对比{{变量名}} 环境变量${函数(参数)} 动态函数
做什么查字典，填固定值调函数，实时生成值
实现方式str.replace() 纯字符串替换正则匹配 + 函数调用
典型例子{{host}} → https://api.test.com${timestamp()} → 1734567890
适用场景环境/配置类固定值（切环境不改用例）每次都变化的动态值（随机手机号、MD5加密）

执行顺序（不能反过来）：永远先换 {{}}，再换 ${}。因为动态函数参数里可能引用了环境变量，比如 ${md5({{token}}+123)}，必须先换掉 {{token}} 才能计算哈希。

一句话：两个花括号查字典，美元花括号调函数。先查后调，查不到报错，调失败留原样。

⭐ 进阶：接口关联代码级实现（4步）

# 步骤1: 初始化变量池 base_variables = build_variables(environment, project) # 全局+局部环境变量 runtime_vars = {} # 空的，等着被填 # 步骤2: 循环每个请求 for suite_request in suite_requests: # 合并：runtime_vars在后，覆盖同名base_variables variables = {**base_variables, **runtime_vars} # 步骤3: 渲染发送 url = render(api_request.url, variables, resolver) # 先{{}}再${} # 步骤4: 提取响应写入runtime_vars extractors = _collect_extractors(suite_request, api_request) if extractors: runtime_vars.update(extract_from_response(response, extractors)) # dict.update() 只追加新key，不同名key全部保留
循环次数执行前 runtime_vars提取了执行后 runtime_vars
第1步 登录{}$.data.token{"token":"abc123"}
第2步 创建用户{"token":"abc123"}$.data.user_id{"token":"abc123", "user_id":42}
第3步 查询{"token":"abc123", "user_id":42}不提取{"token":"abc123", "user_id":42}

核心要点：runtime_vars.update() 是累加的，不清空。第 N 步能看到前 N-1 步提取的所有值。提取失败静默跳过，不中断流程。代码在 request_utils.py 的 extract_from_response()，支持 JSONPath / 响应头 / 状态码 / 正则 四种方式。

🎤 用一句话回答："接口关联怎么实现的？"

我设置一个空字典叫运行期变量池 runtime_vars 来存放 token，先 for 循环按 order 遍历套件里的每个接口，然后合并基础环境变量和运行期变量，调用 render 方法先做 {{}} 环境变量替换、再做 ${} 动态函数解析，用 requests.request() 发请求。拿到响应后调 extract_from_response 提取 token——支持 JSONPath、响应头、状态码、正则四种方式。最后把提取的 token 通过 dict.update() 追加到运行期变量池，下一轮请求合并变量时就能直接用。

核心是 {**base, **runtime} 的字典合并 + extract_from_response 的四种提取。
🧩 追问：基础环境变量是什么？
A: 基础环境变量就是 EnvironmentVariable 表里存的键值对，分 GLOBAL 和 LOCAL 两级——GLOBAL 全局可见、LOCAL 限定项目。执行套件时 build_variables() 把它们查出来拼成字典 {"host":"...", "admin_phone":"..."}，和运行时提取的 runtime_vars 合并。前者是提前配好的不变值（切环境只改表），后者是运行时动态产生的临时值。合并用 {**base, **runtime}，同名时 runtime_vars 覆盖 base。
🧩 追问：for 循环按 order 遍历的作用？
A: 保证接口串行执行——第一步的响应提取完了，第二步才能真正拿到值。比如登录（order=1）先跑，提取 token → 创建用户（order=2）用 token 鉴权 → 查询用户（order=3）用 token+user_id。如果并行跑，token 还没提取出来，下游请求就已经带着空的 {{token}} 发出去了。

一句话：先看Redis能不能连 -> 能连就用Celery(分布式) -> 不能连就开个本地线程跑(降级) -> 同一个核心函数，两种调度方式。

关键代码位置

  • Celery版本：apps/api_testing/tasks.py -> execute_scheduled_task(@shared_task装饰器)
  • 线程版本：apps/api_testing/views.py -> _execute_task_async(threading.Thread)
  • 共同核心：apps/api_testing/tasks.py -> _run_scheduled_task(纯同步函数)

关键技术细节(面试重点！)

  • 核心设计_run_scheduled_task是纯同步函数，不依赖Celery。Celery的@shared_task和threading.Thread只是两种调用它的方式。
  • 工程价值这种设计叫"双通道调度"--有Redis就走分布式(多机器并行)，没有Redis也能单机跑(轻量部署)，兼顾扩展性和易用性。
  • 避免重复两种路径的日志更新、统计更新、通知逻辑完全一致，因为走的是同一个函数。

四、四大核心亮点详解(面试王牌)

4.1 JWT双Token认证 + 无感刷新

面试开场白：
"我们用的是JWT双Token方案。Access Token 60分钟用于日常鉴权，Refresh Token 7天用于刷新AccessToken。同时开了ROTATE和BLACKLIST防重放，登出时主动拉黑。"

用大白话解释(给5岁孩子讲)

想象你去健身房：

  • Access Token(60分钟) = 储物柜手环，进去每次都要刷，但只给你用1小时
  • Refresh Token(7天) = 会员卡，手环过期了拿会员卡去前台换新的
  • ROTATE(轮换) = 每次换新手环，旧手环立即作废(防止别人捡到你的旧手环进去)
  • BLACKLIST(黑名单) = 作废的手环号记在一本黑名单簿上，有人拿旧手环来刷立刻报警
  • 登出 = 你把会员卡交给前台销毁，从此再也换不了新手环

面试可能追问

Q: 为什么不直接用SimpleJWT自带的TokenObtainPairView？
A: 自己写login_view可以让登录接口一次返回user信息+access+refresh，前端不用再单独调用户信息接口。虽然多了几行代码，但减少了网络请求次数。
Q: Refresh Token 7天有效期，不怕泄露吗？
A: 开了ROTATE_REFRESH_TOKENS后，Refresh Token变成"一次性"的--每次刷新都换新的，旧的进黑名单。即使被截获，用一次就失效了。

4.2 变量池引擎(Variable Resolver)

面试开场白：
"我们实现了一个统一变量解析器，语法是${函数名(参数)}，支持60+内置函数。请求进来先合并环境变量，再解析表达式，执行完提取响应字段写回变量池，实现接口关联。"

用大白话解释

想象你是一个翻译官：

  • 请求里写的${random_phone()}不是真的电话号码，是一个"暗号"
  • 变量解析器就是一本文密码本，看到${random_phone()}就替换成13812345678
  • 看到${timestamp()}就替换成当前时间戳
  • 看到${md5(hello)}就替换成加密后的值
  • 上一个请求提取出来的token存在"运行变量池"里，下一个请求写{{token}}就能用

JWT Q1: 登录认证怎么做？
我们用的是 JWT 双 Token 方案。后端基于 rest_framework_simplejwt，登录成功后签发一对 Token：一个短期的 Access Token（60 分钟）用于日常接口鉴权，一个长期的 Refresh Token（7 天）用于刷新 Access Token。

有个实现细节：登录接口我们没有直接用 SimpleJWT 现成的 TokenObtainPairView，而是自己写了函数视图 login_view——先用自定义的 LoginSerializer 走 Django authenticate() 校验用户名密码和 is_active，校验通过后再用 RefreshToken.for_user(user) 手动签发 Token 对。这样做的好处是登录响应里可以一并返回用户信息，前端一次请求就能拿到 user + access + refresh。

Q2: Refresh Token长期有效，怎么防重放？
A: 两个配置：ROTATE_REFRESH_TOKENS=True让每次刷新都换新Token，旧Token作废；BLACKLIST_AFTER_ROTATION=True让旧Token进黑名单持久化到数据库。这样即使Refresh Token被截获，用一次就失效。另外登出时主动blacklist，双向防护。
⭐ 导师原版
JWT Q2: 防重放怎么做？
我们开了两个关键配置来防重放：
ROTATE_REFRESH_TOKENS=True：每次调刷新接口，都会签发一个新的 Refresh Token，旧的作废。
BLACKLIST_AFTER_ROTATION=True：旧的 Refresh Token 轮换后自动进黑名单（依赖 SimpleJWT 的 token_blacklist app，落到数据库表里）。

这样 Refresh Token 是"一次性"的，即使被截获，用过一次就失效了。另外登出时，前端会把当前 Refresh Token 放在请求体发给后端，后端调 token.blacklist() 主动拉黑。

Q3: 接口测试模块的核心流程是什么？
A: 请求进来首先合并环境变量(全局+局部)，然后变量解析器把${xxx}表达式替换成实际值，接着组装HTTP请求发出去，收到响应后做断言验证，同时把需要的字段(比如token)提取到运行时变量池，供下一个请求引用。所有请求跑完后生成Allure报告。关键设计是变量池分两层：base_variables是环境变量，runtime_vars是运行时提取变量，后者覆盖前者。

API Q1: 接口测试怎么执行一个请求？
后端用同步的 requests 库执行。用户在前端配置好 URL、方法、Header、Params、Body，后端拿到后做变量替换，再用 requests.request() 发出去，超时统一 30 秒。

HTTP 全方法：GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS。
Body 两种模式：json（用 json= 自动序列化）和 raw（用 data= 发原始串）。Header 兼容新版数组格式和旧版对象格式两种写法。

WebSocket 我们也做了真实执行——用 websocket-client 封装独立执行路径：建立连接、发送消息、接收响应、超时控制，请求类型是 WEBSOCKET 时自动走这条路径，而不是当 HTTP 发。

调度器不算时间，委托给模型方法。每个任务有 next_run_time，should_run_now() 判断"ACTIVE 且当前时间 ≥ next_run_time"。执行完再 calculate_next_run()：CRON 用 croniter 算、INTERVAL 用 timedelta、ONCE 返回 None。
防卡死：任务命中后先落库更新统计再执行，无论成功失败都会重算 next_run_time。
Q4: 变量池是怎么实现接口关联的？
A: 每个请求执行完，通过extract_from_response把响应中的字段提取出来(支持JSONPath)，写入runtime_vars字典。下一个请求渲染时，合并{**base_vars, **runtime_vars}，就能直接引用上一步提取的值。比如登录接口提取token，后续接口在Headers里写Bearer {token}就能用。
Q5: 定时任务是怎么调度的？
A: 做了Celery+线程的双通道调度。核心函数_run_scheduled_task是纯同步函数，Celery的@shared_task和threading.Thread只是两种调用方式。如果Redis broker可用就走Celery分布式执行，不可用就降级为本地线程。这样既支持多worker扩展，又能在轻量部署时不依赖中间件。
Q6: 你们的AI用例生成是怎么做的？
A: 用户上传需求文档(PDF/Word/TXT)，先由DocumentProcessor提取纯文本，然后走AdvancedTestRequirementAnalyzer的多阶段分析流水线：预处理->需求提取->结构化->质量评估->风险分析。拿到结构化需求后，AIService.generate_test_cases根据需求类型生成对应的测试用例。过程中做了三层容错：截断续写(长文本分片)、生成后校验(case_id去重)、超时降级(AI挂了走fallback)。
Q7: 这个项目用了哪些设计模式？

A: 踩过两个典型的。第一个是后台线程里跑UI自动化时，数据库连接会断——因为Django的连接是按请求管理的，线程里没有。解决方法是执行前把数据从ORM对象拍平成字典，执行后手动关连接。第二个是Windows上生成的测试报告中文乱码，原因是变量解析器输出没设编码，在初始化时加了UTF-8设置就好了。

Q10: 断言有哪些类型？怎么实现的？

Q12: 前端是怎么管理状态的？Token放哪里？

Q13: 为什么用JWT而不用DRF自带的Token？
A: DRF自带的Token是存在数据库里的随机字符串，每次请求要查数据库验证，无状态性差。JWT是无状态的，只要验签名就能确认身份，不用每次都查数据库，性能更好。而且JWT可以携带payload信息(比如user_id、exp过期时间)，更灵活。
Q14: 简单说一下Celery的工作原理？
A: Celery有三个角色：Producer(我们的Django应用，发任务)、Broker(Redis，存任务队列)、Worker(独立进程，消费任务)。我们的tasks.py里用@shared_task装饰器注册任务，调用.delay()把任务扔到Redis队列，Worker从队列取任务执行。配置在settings.py里，CELERY_BROKER_URL指向Redis。
Q15: 你们怎么处理跨域(CORS)？
A: 用django-cors-headers中间件。开发环境允许localhost:3000和localhost:8080，生产环境从环境变量读CORS_ALLOWED_ORIGINS。同时因为支持SSE(Server-Sent Events)，额外加了cache-control的CORS头。
Q16: 这个项目的日志是怎么做的？
A: Django的logging模块，配了三种handler：console(开发调试)、file(app.log存info以上)、error_file(error.log单独存错误)。每个关键模块有各自的logger，比如apps.api_testing.views单独配置。
Q17: 如果让你新加一个测试功能模块，你会怎么做？
A: 按现有模式来：先在apps/下建新App->定义models(数据表)->写serializers(序列化)->写views(ViewSet)->配urls(路由)->注册到settings.py的INSTALLED_APPS->注册到backend/urls.py的总路由。如果有异步任务就写tasks.py，如果有定时任务就复用ScheduledTask体系。

Q20: 为什么选择Django而不是FastAPI？
A: Django的特点是"全家桶"--ORM、Admin后台、认证系统、中间件都是开箱即用的，适合快速构建功能完整的平台。FastAPI更轻量，适合纯API服务。这个项目需要Admin后台管理、复杂的Model关系、多App模块化，Django更合适。不过异步处理方面，Celery弥补了Django同步的不足。

◆ 3.1 JWT 双 Token 鉴权（简历对应："Access/Refresh双Token+无感刷新+黑名单防重放"）

Q补01: 你说实现了双 Token 鉴权，具体流程是什么样的？从登录到登出讲一遍。
A: 用户登录时我们手动签发一对 JWT。LoginSerializer 做三层校验——非空、密码正确、is_active 有效。全通过后用 RefreshToken.for_user(user) 手动签发，一次接口返回 user + access + refresh，前端不用二次请求。使用期间每次请求 Axios 拦截器自动带 access，响应 401 时用 refresh 换新双 Token，更新本地存储后重发——用户无感知。登出时前端发 refresh，后端调 token.blacklist() 把 jti 写入数据库黑名单表。
Q补02: 为什么不用 SimpleJWT 自带的 TokenObtainPairView，要自己写 login_view？
A: 自带的 View 只返回 access 和 refresh，前端还要再发一次请求拉用户信息。自己写 login_view 可以一次请求把 user + access + refresh 全返回，减少一次网络往返。这是工程优化——不是什么高级技术，但能提升用户体验。
Q补03: Token 黑名单是怎么实现的？如果数据库挂了黑名单还有效吗？
A: 靠 SimpleJWT 的 blacklist app，用 OutstandingToken 和 BlacklistedToken 两张表存储。刷新或登出时把 Token 的 jti（JWT ID）插入 BlacklistedToken 表，后续任何请求校验时都会先查这两张表。数据库挂了确实是黑名单方案的缺陷——但 ROTATE_REFRESH_TOKENS 让 Refresh Token 本身就是一次性的，即使黑名单短暂失效，攻击窗口也非常有限。这是可用性和安全性之间的权衡。
📖 学习版
Q补04: 无感刷新具体怎么做的？刷新期间用户连续发多个请求怎么办？
A: Axios 响应拦截器收到 401 时，如果正在刷新中就返回一个 Promise 放进 pendingRequests 队列，刷新成功后批量 resolve 队列里的所有请求，各自带上新 Token 重发。如果在刷新中又有新请求进来，不会重复触发刷新——用 isRefreshing 标记位和 pendingRequests 数组来控制。
⭐ 导师原版
JWT Q3: 前端怎么做到 Token 过期无感刷新？（高频深挖）
核心是在 Axios 里用一个标志位 + 一个请求队列解决并发刷新问题。

全局维护两个变量：isRefreshing（布尔，当前是否正在刷新）和 failedQueue（数组，存放刷新期间被挂起的请求）。

请求拦截器做"预刷新"：每个请求发出前，如果检测到 Token 快过期（5 分钟内）：
· 如果当前没在刷新，就置 isRefreshing=true，去调刷新接口，刷新完用新 Token 放行；
· 如果已经在刷新了，就把当前请求包成一个 new Promise，把它的 resolve 塞进 failedQueue 挂起——请求就"卡"在这个未决的 Promise 上不发出去。

等刷新成功，调用 processQueue(null, newToken) 遍历队列，逐个 resolve(newToken)，把挂起的请求用新 Token 唤醒重放。

响应拦截器做兜底：如果请求已经返回 401，且没重试过（用 originalRequest._retry 标志防止无限重试），就触发刷新后用 api(originalRequest) 重放原请求。

进阶：并发 401 补全——当 isRefreshing 为 true 时，401 请求不会被直接登出，而是同样挂入队列，等刷新完成后用新 Token 重放。这样并发 401 场景下也能保证请求不丢失。
进阶：exp 解析——过期时间通过解析 JWT payload 的 exp 字段来算，atob 解码时处理了 base64url（-→+、_→/），拿到 exp（秒）转毫秒时间戳，前后端完全同步。
Q补05: Access Token 设 60 分钟、Refresh 设 7 天，这个时间是怎么定的？
A: Access 60 分钟是在泄露风险和用户体验之间取平衡。如果设 5 分钟，刷新请求太频繁；如果设 1 天，一旦泄露攻击者有整整一天的时间窗口。60 分钟刚好够一个长会议跑完。Refresh 设 7 天覆盖正常工作周——周五下班到周一上班不用重新登录。
⭐ 导师新增
JWT 新增 Q: 登出怎么防止死循环？（导师原题 Q4，高频追问）
A: 登出设计了三层防护：
第一层：模块级 isLoggingOut 标志位，防止 logout 被并发重复调用；
第二层：只有在 Token 未过期时才发登出请求给后端——因为如果 Token 已过期，发出去会返回 401，又会触发拦截器的刷新/登出逻辑，形成连锁；
第三层：响应拦截器对 /auth/logout/ 和 /auth/token/refresh/ 这两个接口的 401 做了特判，直接清本地状态跳登录页，不再进入刷新分支。
背诵关键词：isLoggingOut / 过期不发 / 特定路径特判。

◆ 3.2 接口测试（简历对应："支持在线写用例、接口测试、自动化驱动+用例编写"）

Q补06: 你们的接口测试是怎么跑起来的？从用户点执行到看到报告，发生了什么？
A: 用户点执行后，后端开守护线程异步执行，立刻返回"任务已开始"。线程里先从数据库查出套件包含的接口列表按 order 排序。逐个执行：先合并环境变量 base_variables（4层合并：全局→局部→手动选定→运行时动态），再把 {{base_url}} 替换为真实值、${timestamp()} 替换为函数返回值。URL/Headers/Body 全渲染完后用 requests.request() 发 HTTP 请求。拿到响应后按配置的提取规则（JSONPath/Header/正则/状态码）把关键字段写入 runtime_vars，再跑 6 种断言验证。最后把请求和响应全量存到 RequestHistory 表。全部跑完生成 Allure 报告。
Q补07: 接口关联怎么实现的？比如登录拿到 token，下一个接口怎么用？
A: 核心靠 runtime_vars 字典。每个请求执行前合并 {**base_variables, **runtime_vars}——base 是环境变量，runtime 是前面请求提取的。请求执行后用 extract_from_response 从响应里提取字段写入 runtime_vars。第一个请求登录返回 {"data":{"token":"xxx"}}，配置 $.data.token 提取规则，提取后 runtime_vars['token'] = 'xxx'。第二个请求 Header 里写 Authorization: Bearer {{token}}，渲染时从 runtime_vars 取出来替换。
Q补08: 渲染的时候 {{xxx}} 和 ${xxx()} 有什么区别？先后顺序呢？
A: {{xxx}} 是环境变量的占位符，从变量字典里查值替换。${xxx()} 是动态函数调用，调用 VariableResolver 里注册的 60+ 个函数。顺序是先替换环境变量，再解析动态函数——因为动态函数的参数里可能包含环境变量，比如 ${md5({{secret}})}。
Q补10: 如果接口依赖链很长（A→B→C→D），中间某个接口失败了怎么办？
A: 当前实现是顺序执行的，中间某个接口失败会抛异常，后面的接口不会继续跑。这个设计是故意的——因为接口依赖链中，上游失败意味着下游数据不完整，继续跑没有意义，反而会产生误导性的失败报告。执行记录里会标记每条接口的 passed/failed，用户可以快速定位出问题的节点。

◆ 3.3 Celery + 线程双通道（简历对应："dispatch()优先Celery、broker不可用自动回退线程，兼顾扩展性与轻量部署"）

Q补11: dispatch() 优先 Celery、不可用时回退线程——具体怎么判断 Celery 不可用？⭐ 导师API Q3
A: dispatch() 函数里用一个 try-except：先调 celery_task.delay() 把任务扔进 Redis 队列，如果 Redis 连接失败、kombu 抛链接异常就被 catch 住，然后用 threading.Thread 直接本地执行 fallback 函数。不需要主动 ping Redis——delay 失败本身就是信号。
Q补12: Celery 和线程执行的区别是什么？为什么不全部用线程？⭐ 导师API Q3
A: 区别在于执行位置和资源隔离。Celery 的任务在独立 Worker 进程里跑，和 Django 主进程完全隔离——一个接口测试崩溃不会影响 Web 服务。线程跑在 Django 进程里，共享内存，崩溃可能导致整个 Django 挂掉。但线程的优势是零依赖。为什么不全部用线程？因为生产环境需要资源隔离。为什么不全部用 Celery？因为开发环境和轻量部署时可能没装 Redis。双通道就是两种场景都照顾到。
📖 学习版
Q补13: 你简历写"统一调度 API/UI/APP 三类定时任务"——是怎么统一管理的？
A: 通过一个 Django 管理命令 python manage.py run_all_scheduled_tasks，在一个 while True 循环里每 60 秒分别调 schedule_api_tasks()、schedule_ui_tasks()、schedule_app_tasks()。每个方法查各自模块的 ScheduledTask 表，用同一个 dispatch() 函数分发。对调度员来说，API、UI、APP 只是三个不同的任务来源，分发逻辑完全一样。
⭐ 导师原版
API Q3: 三个模块的执行机制一样吗？
三个模块统一调度、统一执行通道：API、UI、APP 任务都走 Celery 异步分发（.delay()）。我抽了个 dispatch() 函数——优先 Celery，broker 不可用时自动降级到 threading 线程执行，保证没起 worker 时系统照常工作。

为什么统一到 Celery？因为 UI/APP 自动化是重任务（跑真实浏览器/设备、耗时长），用 Celery worker 异步执行能水平扩展、任务不阻塞调度器。但我不想硬依赖 broker，所以做了 dispatch() fallback——celery task 和线程 fallback 共用同一个执行函数、同一套参数签名，broker 连不上就退回线程。这是可用性和扩展性的平衡。
📖 学习版
Q补14: CRON、INTERVAL、ONCE 分别怎么计算下次运行时间？
A: CRON 用 croniter 库解析 cron 表达式（如 0 8 * * *），根据当前时间算出下一次触发时间。INTERVAL 直接 now + interval_seconds。ONCE 只看 execute_at，当前时间还没到就返回那个时间，已经过了就返回 None 不再执行。每次跑完 update_run_stats 都会重新计算 next_run_time 并存回数据库。
⭐ 导师原版
API Q2: 调度器怎么判断任务该执行？怎么算下次时间？
每个任务有 next_run_time 字段，should_run_now() 判断"状态是 ACTIVE 且当前时间 ≥ next_run_time"。执行完再调 calculate_next_run() 重算下次时间：
· CRON：用 croniter 解析 cron 表达式算下一次；
· INTERVAL：now + timedelta(间隔秒数)；
· ONCE：到点后返回 None，之后就恒不执行。

防卡死设计：任务命中后先落库更新统计再执行，并且无论成功失败都会重算 next_run_time，避免某次执行异常导致 next_run 没更新、任务永久卡住。
Q补15: 调度扫描间隔 60 秒，如果任务设定 8:00:00 跑，但调度器 8:00:30 才扫到它，会延迟 30 秒吗？这算 Bug 吗？
A: 会的，精度就是 ±60 秒。对测试平台的定时任务来说，30 秒延迟完全可接受——这不是高频交易系统。如果追问怎么改进，可以说换成 Celery Beat 可以达到秒级精度，但引入了额外的 Redis 依赖，和"轻量部署"的设计目标冲突。
Q补16: 如果任务执行时间超过 60 秒（扫描间隔），会发生重复执行吗？怎么解决？
A: 当前实现有这个隐患——should_run_now() 只检查 next_run_time <= now，不检查任务是否正在执行。如果任务跑了 90 秒，下一轮扫描时 next_run_time 还没更新（因为 update_run_stats 在任务结束时才调用），调度器会再触发一次。改进方案：在 ScheduledTask 表加一个 is_running 字段，should_run_now 时一并检查；或者在创建 TaskExecutionLog 前先查是否已存在 RUNNING 状态的日志。
Q补17: 你们 Celery 是怎么启动的？Worker 和 Beat 有什么区别？为什么没用 Celery Beat？
A: Worker 用 celery -A backend worker -l info 启动，负责从 Redis 队列取任务执行。Beat 是 Celery 的定时调度组件，可以按 beat_schedule 定时触发任务。我们没用 Celery Beat，而是自己写了 run_all_scheduled_tasks 管理命令做调度——这样可以统一管理 API/UI/APP 三类任务的调度逻辑，集中日志和监控。

第六章补充2：3.4 AI需求分析 → 用例生成 面试话术（7题）

面试策略：这7道题不需要全背，面试官通常只追问2-3个。重点记住整体流程、OpenAI兼容协议、三层防御、自动降级这四个关键词就够了。
Q补18: 这个AI功能是怎么实现的？整体流程说一下
A: 用户上传需求文档后，系统先用 PyPDF2 或 python-docx 把文字提取出来，然后调大模型的 API 去做两件事：第一，从文档里提取出结构化的需求点，比如"用户登录功能、优先级高、验收标准是什么"；第二，根据这些需求点逐条生成测试用例。全程如果有任何一步 AI 挂了，会自动降级到本地兜底数据，保证流程不中断。
关键词：上传→提取→AI分析→AI生成→入库。
Q补19: 你们支持哪些大模型？怎么做到统一接入的？
A: 支持 DeepSeek、通义千问、硅基流动、智谱。接入方式是统一的——所有模型都走 OpenAI 兼容协议的 /v1/chat/completions 接口。也就是说，不管底层是哪个厂商的模型，代码里只写一套 HTTP 请求逻辑：传 API Key、传 messages、收 choices 里的回复。新增模型只需在数据库配置表加一条记录，零代码改动。
关键词：OpenAI兼容协议、一套代码多模型、配置化接入。
Q补20: AI返回的内容不稳定怎么办？你们怎么处理的？
A: 做了三层防御。第一层，大模型有时会在 JSON 外面包 markdown 代码块标记（```json...```），用正则剥掉。第二层，剥离后用 json.loads() 解析，失败就抛异常走兜底。第三层，解析成功后做字段规范化——AI 返回的字段名可能不标准，比如返回 "priority":"高"，我们的数据库存的是 "high"，需要映射表统一转换，缺字段补默认值。
关键词：去代码块→JSON解析→字段规范化。
Q补21: 如果AI接口超时了怎么办？
A: 调用 AI 设了 120 秒超时。超时或报错后，异常被最外层 try-except 捕获，自动切换到本地兜底逻辑——返回几条模拟数据。好处是：AI 挂了用户至少能看到分析结果，系统不会白屏或报 500。
关键词：120秒超时、异常捕获、自动降级到mock。
Q补22: 测试用例具体是怎么生成的？
A: AI 先从文档提取需求点存到数据库，用户在前端勾选需求点点"生成"。系统逐条调 AI，把需求描述当输入，让 AI 输出标准格式用例（编号、标题、步骤、预期结果）。生成后做两件事：一是 case_id 去重，重复自动加后缀；二是可选配另一个 AI 模型评审打分，通过才算合格。
关键词：需求提取→逐条生成→ID去重→可选评审。
Q补23: Django是同步框架，怎么调用异步的AI接口？
A: 在独立线程里用 asyncio.new_event_loop() 新建事件循环，然后 run_until_complete() 等异步调用跑完，主线程阻塞等待。这样不用把整个 Django 改异步，又能正常调异步 AI 接口。
关键词：独立线程 + 新建事件循环 + run_until_complete。
Q补24: 这个功能你觉得最大的难点是什么？
A: 最大难点不是调 AI，而是保证整个链路的健壮性。AI 接口会超时、会返回乱格式、会字段名不标准。所以设计核心是"永远有兜底方案"：调用有超时控制，解析有正则清洗，字段有规范化映射，最外层有 mock 降级。任何一个环节出问题，系统都能继续服务。
关键词：健壮性、兜底方案、不中断。

第六章补充3：UI 自动化双引擎统一抽象 · 12种定位策略 · POM 页面对象（6题）

2026-09-22 新增 | Q1 双引擎统一抽象 / Q2 12种定位策略 / Q3 POM 代码生成
Q补25: UI 双引擎（Selenium + Playwright）怎么统一抽象的？
A: 入口是 TestExecutor 类，构造时接收 engine 字段，run() 里根据它是 Playwright 还是 Selenium 来分发执行。统一契约不是接口多态，而是统一的数据结构约束：执行前先把 ORM 里的测试步骤预取拍平成纯字典 step_data（含 action_type、input_value、定位信息），两个引擎的 execute_step 都吃这个字典，返回统一结构的 step_result（success/error）。动作语义统一（click/fill/waitFor/assert），Playwright 用 page.click()、Selenium 用 element.click()，各用自己的 API 实现同一套语义。

关键设计：为什么要预取拍平？因为 Playwright 在后台线程里跑，Django ORM 的连接是线程局部变量（thread-local），每个请求一个连接。后台线程没有请求上下文，访问 ORM 会报连接冲突。所以进浏览器之前把数据全读出来变成字典，connection.close() 关掉连接。字典没有数据库连接的"尾巴"，哪个线程都能用。
关键词：step_data 字典契约、step_result 统一返回、connection.close() 防线程冲突、语义统一 API 各自实现。
🧩 追问：ORM 是什么？怎么体现的？
A: ORM = 对象关系映射，不写 SQL，用 Python 对象操作数据库。看到 .objects. 就是 ORM（如 TestSuite.objects.create()），看到 .select_related() 就是 ORM 做跨表 JOIN（如 steps.select_related('element', 'element__locator_strategy')）。预取拍平那一行 select_related 一次 JOIN 查出三张表（TestCaseStep → Element → LocatorStrategy），然后把值取出来放字典。注意：step.element.locator_value 这种写法是在读值，不是把 ORM 对象放字典——读完后只有字符串留在字典里，connection.close() 后子线程直接读字典不报错。
🧩 追问：不拍平会怎样？
A: 主线程创建了数据库连接 → 子线程（Playwright）里访问 ORM 对象 → 子线程没有自己的连接 → 报错。Django 的数据库连接是 thread-local 的，每个线程独立。解决办法：进子线程前一次性读完数据、拍成纯字典、connection.close()。字典是纯 Python 数据，跨线程随便用。核心：ORM 对象有数据库连接的"尾巴"，字典没有。
Q补26: 12 种元素定位策略怎么实现的？
A: 用管理命令 init_locator_strategies 一次性写入 LocatorStrategy 表：6 种通用（ID/CSS/XPath/name/class/tag）+ 6 种 Playwright 专用（text/placeholder/role/label/title/test-id）。
Playwright 侧直接调语义化 API：get_by_text()、get_by_role()、get_by_placeholder() 等，text/role 等策略走原生，不转 XPath。
Selenium 侧用 strategy_map 字典把策略名映射到 By.ID/By.CSS_SELECTOR 等（如 strategy_map.get('id') → By.ID，就是查表）。Selenium 没有 text/role 原生 API，text 策略动态降级成 XPath：//*[contains(text(), '登录')]，不是预设的，是运行时用模板 `//*[contains(text(), '{值}')]` 动态拼接。还有自动纠错：值以 // 开头时强制改策略为 xpath——相信值比相信策略名更可靠。
关键词：管理命令初始化、字典映射 strategy_map、text 降级 XPath 动态拼接、自动纠错。
🧩 追问：备用定位器 + el-select 启发式识别怎么做的？
A: 备用定位器：Element 表有个 backup_locators JSON 字段，格式 [{"strategy":"id","value":"btn"}, {"strategy":"xpath","value":"//button"}]。主定位失败自动试备用——前端改个 class 名不会让整个用例挂掉。为什么不建多条 Element 记录？因为一条 Element + JSON 数组比 N 条 Element 好维护，且语义正确（备用是同一元素的另一种找法）。
el-select 启发式识别：Element Plus 的 el-select 不是原生 <select>——选项在点击后才动态弹出一个浮层。代码用关键词检测（if 'el-select' in locator_value）自动判断类型，识别后点击内部触发器 .el-select__wrapper，等 800ms 弹层展开，再在 .el-select-dropdown__item 里找选项。跟你学的 Select(element).select_by_index() 不同——那个是原生 select，这个是组件库下拉框。
关键词：backup_locators JSON 数组、主失败试备用、el-select 关键词检测、先触发器再弹层。
Q补27: POM 页面对象模式怎么落地的？
A: 我们的 POM 是代码生成型，不是运行时代理。PageObject 表存类名和 URL 模式，PageObjectElement 中间表把 Element 关联到 PageObject 下并配方法名，generate_code() 把它渲染成可运行的 Python/JS 页面对象类代码。

关键：POM 主要用于导出可读的 PO 类代码，运行时执行仍走 Q1 的 step_data 字典路径——POM 是输出出口，不是执行入口。
生成方式很简单：循环取 self.page_object_elements.all()，把 method_name 和 locator_value 拼进字符串模板：def {method_name}(self): return self.page.locator('{locator_value}')。
JS 版多了 is_property 控制：True → 拼在 constructor 里面作为属性（this.btn = page.locator(...)），False → 拼在外面作为 async 方法（async click() { return ... }）。

跟执行引擎的关系：两套独立数据源——TestCaseStep → step_data → 执行引擎；PageObjectElement → generate_code() → 导出代码。删了 PageObjectElement 不影响执行，加了 TestCaseStep 不影响 POM 生成。
关键词：代码生成（非运行时代理）、字符串拼接、is_property 控制 constructor 内外、独立于执行引擎。

七、改进方向(面试必问加分题)

如果被问"这个项目有什么可以改进的地方？"--选2个回答即可。

方向1：接口编排可视化

目前接口关联是配置式的(JSON里写提取规则)，下一步可以做成拖拽式可视化编排画布。让不写代码的测试同学也能通过连线来编排复杂链路，降低使用门槛。

方向2：执行耗时精确采集

Allure报告目前基于执行结果合成耗时，可以在执行链路里打点采集每步真实耗时(DNS解析、TCP连接、请求发送、响应接收)，让性能分析更精确。

方向3：AI视觉模式成本优化

UI自动化的视觉模式调多模态模型成本较高，可以做"文本模式优先、失败自动升级视觉模式"的降级策略。比如先用DOM解析尝试定位元素，找不到再截图用视觉模型，平衡成本和成功率。

方向4：分布式锁与任务幂等

多worker场景下，定时任务可能被多个worker同时拉取。可以加分布式锁(Redis SETNX)避免重复执行，同时在任务上做幂等标记。
